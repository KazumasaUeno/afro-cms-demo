## 3. live をデモの画面にする

### 3.1 経路と状態ごとの中身（`LiveRequirementsPage.tsx`）

今は draft のときだけ `AiDraftPanel` を出し、それ以外はヒアリングの画面へ転送している（`LiveRequirementsPage.tsx:55`）。これを**デモの `RequirementsDocPage` と同じ骨組み**（戻る導線 → `PageHeader`「要件定義書」→ `RequirementsHowTo` → `Tabs` 4 つ）に置き換え、全状態をこの画面で出す。

| 状態 | 「1. 改善提案」タブ | 右上の操作（デモの `RequestApprovalButton` の位置） | つくり方の「いまここ」 |
|---|---|---|---|
| draft・下書きなし／生成中／失敗 | デモの空の状態の `Surface`（`RequirementsDocPage.tsx:52-61`）の中に `AiDraftPanel` の生成・生成中・失敗の表示 | なし | 2. AI がたたき台を作成 |
| draft・下書きあり | §3.2 の編集（表示／編集） | 「内容を確認した」→「承認を依頼する」（`AiDraftEditor` の主操作を移す）＋保存の状態 | 3. 内容を確認して承認を依頼 |
| analyzed（承認待ち） | `ProposalView`（保存した提案） | 「お客様の承認待ち」の表示（今の `ProposalView.tsx:202-207`） | 4. お客様が承認 |
| approved | `ProposalView` | なし | すべて済み |

- `RequirementsHowTo` は `requested` を demo の state から取っている（`RequirementsDocPage.tsx:40`）。live では `status==='analyzed'` を依頼済みとして渡す（今の live の completeAnalysis＝承認の依頼）。draft で下書きがあるときは 3 段目を「いまここ」にするため、`current` を外から渡せるようにする（見た目は変えない）
- 「ヒアリングに戻る」は今の未保存を送ってから移る処理（`LiveRequirementsPage.tsx:47-51`）を「プロジェクト詳細」と「回答を見直す」の両方に掛ける
- 2〜4 のタブは live でも同じ部品。3. スケジュールは live に日程が無いので「承認後に入力します」の文（`RequirementsDocSections.tsx:64`）
- ヒアリング画面の result（見出し「AIがまとめた改善提案」`RequirementsPage.tsx:68`）は、live ではこの画面へ転送する（同じ内容が 2 か所に出ないように）[INFERENCE。ユーザー決定「本番もデモと同じ」から。lead-architect 確認]

### 3.2 編集（draft・下書きあり。「1. 改善提案」タブの中）

- タブの中の一番上に `ToggleButtonGroup`「表示／編集」（今の `AiDraftEditor.tsx:180` と同じ部品）。**「表示」はお客様に出る形そのもの**（§2。要確認の数字だけ `<mark>`）で、今の右側のプレビュー列（`AiDraftEditor.tsx:236-242`・`:258-270`）の代わり。既定は表示（2026-11-26 ユーザー決定）
- 「編集」は §2 と**同じ `Surface`・`SectionTitle`・`KeyValueRows` の並び**のまま、`v` の中身だけを入力にする:
  - 要約・改善ポイント: 今の `AiDraftEditor.tsx:169-201` の欄（`Field`・分野・優先度）
  - 項目: 状態の `ToggleButtonGroup`（個別＝確定案／未確定／対象外、選択＝採用案／未確定／不採用）＋`Field`（`{n} / 400文字`。t22-01 は `REQ_DOC_LIMITS.openItemsText`）＋caption で確認対象・書いた元（「AI の下書き」「ヒアリングの選択肢・案件情報から転記」「担当者が記入」）・根拠のチップ（`AiDraftEditor.tsx:191-196` の形）＋`FlagLine`
  - **固定は入力も状態の操作も出さない**（表示と同じ「確認中」の行）。検査の正は `functions/src/ai/reqDocEditable.ts:67-68`
  - AI追加: `AiBadge label="AI追加"`＋項目名（1〜40 字）・採用案／不採用・内容・理由（≤200）＋削除（確認 `Dialog`「この追加項目を削除しますか？ 作り直さない限り元に戻せません。」）。**新しく足すボタンは出さない**（Q-8・`reqDocEditable.ts:76-95`）
  - 特記事項（章末の行）・表紙 4 欄（表紙の `Surface` の中、helperText「会社名と役職まで（氏名は入れません）」）
- 対象外・不採用で理由が空: 欄に error「対象外（不採用）にするときは理由を書いてください」。その間は自動保存を送らない（送ると `reqDocEditable.ts:72` で拒否）。保存の状態に「理由が未入力の項目が {n} 件あります。入力すると保存します」
- 自動保存・作り直す・エラー文言は今の `AiDraftEditor` のまま（置き場所だけ右上の操作の横へ）

### 3.3 提出前に必須の章（01・02・19・21）

- 画面: 未確定（`open`・文が空の `proposed`）が残る間は「承認を依頼する」を押せない。理由（ボタンの下の caption、今の `AiDraftEditor.tsx:131-133` の形）:「01・02・19・21 章に未確定の項目が {n} 件あります。埋めると承認を依頼できます。」。編集の章の `SectionTitle` の sub に「提出前に必須」の `StatusPill`
- **サーバーでも拒否する**（lead-architect 決定。末尾）。置き場所は U3 の結果を見て U4 の計画で決める
- 確認ダイアログの本文に 1 行:「未確定 {m} 件・確認中 {k} 件のまま、お客様に提出します。」

### 3.4 お客様ポータル（`PortalApprovalPage.tsx`）

- 見出し「確認・承認」（`:26-31`）と準備中の表示（`:32-33`）は今のまま。承認待ち・承認済みは `ProposalView variant="client"`（`:36`）を**同じ 4 つのタブ**で囲む（2〜4 はデモと同じ部品）。「つくり方」は開発者の手順なので出さない。承認の履歴（`:37`）はタブの下
