## 1. O-2: WBS の保存の競合のあと下書きが古いまま

- 再現（修正前 5181）: admin 2 人（A・B 別 context）で `reqdoc-v3-approved` の `/schedule`。A がデザインのバーを → で 1 日動かす（未保存）→ B が 2 日動かして「WBS を保存」（editSeq 4→5）→ A が「WBS を保存」→「ほかの人が先に保存しました。最新を読み込みました」。**A のバーは自分の下書き（12/2〜12/8）のまま・「未保存の変更があります」のまま**。もう一度動かして保存しても再び競合（editSeq 5 のまま）
- 直接原因: `WbsSection.tsx` の保存は失敗（false）と競合を区別せず、競合でも下書きを残す。token は「下書きが dirty の間は追従しない」（:163 の effect）ので、版も古いまま → 何度保存しても競合
- 根本原因: `WbsSource.save` / `ScheduleSource.save` の戻り値が boolean だけで、競合（`ScheduleConflictError`）を画面に伝える手段が無かった。文言（repositories 側）と画面の状態（WbsSection 側）を別々に決めていた
- 事前に検出できなかった理由: 競合の確認（QA C1・C2）は「上書きされない」ことだけを見ていて、競合の後にもう一度保存できるかを見ていなかった（テスト漏れ）
- 修正:
  - `src/features/schedule/scheduleSource.ts`: `SaveResult = boolean | 'conflict'`・`closesAfterSave`
  - `src/live/pages/LiveSchedulePage.tsx`: WBS の保存と予定日の `run` が `ScheduleConflictError` を `'conflict'` で返す。理由のダイアログは `ok === true` のときだけ閉じ、再計画の競合だけは閉じて最新を出す（取り下げ・代理承認は今までどおり開いたまま）
  - `src/features/schedule/WbsSection.tsx`: `'conflict'` なら下書き・完了印の下書きを**応答の時点の**保存済み（ref）に置き換える。dirty でなくなるので token と後から届く最新は既存の effect で追従する
  - `src/features/schedule/ScheduleView.tsx`: 予定日の入力画面・◆ の下書きも `'conflict'` で閉じる（§5 4a の「B のダイアログが開いたまま」と同じ扱いにそろえた）
  - demo（source なし）は変更なし（同期の true / false のまま）
- 確認（修正後 5182・同じ手順）: 競合の文言の後、A のバーは B の値（12/5〜12/11）・「未保存の変更」なし。A がもう一度動かして保存 →「WBS を保存しました」（editSeq 6→7）、B の画面にも A の値が出る。コンソールの error / warning 0 件
- 予定日（納品予定日の入力画面）: 修正前は A の画面が開いたままで、同じ画面で保存し直すと再び競合（internal.editSeq 3 のまま）。修正後は競合で画面が閉じ、カードは B の 12/26。開き直して保存 →「スケジュールを変更しました」（editSeq 4→5・12/27）
- スクショ（コミットしていない）: スクラッチの `shots-post/o2_A_after_conflict.png`・`o2d_A_after_conflict_{before,after}.png`

## 3. seed: `reqdoc-v3-draft` の edited がサーバーの検査に通らない

- 再現: 修正前の seed の generated / edited を `validateEditableV3`（functions/src/ai/reqDocEditable.ts）に通すと 3 件とも `points[1].evidence` で拒否（単体テストで確認）
- 原因: ① 改善ポイント ai2 の根拠に `site_text`（v3 の項目にだけ使えるキー。改善ポイントは `AI_EVIDENCE_KEYS` だけ）② human の項目で generated の by が `ai`・edited で by／根拠を変えていた（サーバーは by・evidence の書き換えを拒否。本物の generated は `open('human')`）③ 担当者が追記した例の項目で by を `human` に変えていた
- 根本原因: seed の文書の形を Rules テストの fixtures に合わせただけで、サーバーの検査（functions）には一度も通していなかった
- 修正: `scripts/seed-emulator-reqdoc.mjs`（ai2 の根拠を `q-issue`・`q-cv`、human の項目は generated で by `human`・根拠なし、追記の例は by を変えない）。import しても書き込まないよう main を `isMain` で囲み、`seedDraftOf`・`SITES` を export
- 確認: 単体テストで 3 件とも検査に通る。エミュレータ（修正後の seed）で admin が `reqdoc-v3-draft` の要件定義書を「編集」→ 入力欄（126 個）の 1 つに追記 → 自動保存 → 読み込み直して「編集」→ 追記が残っている。Firestore（REST）の `aiDrafts/requirements` にも追記の文字列がある。functions のログに検査エラーなし
